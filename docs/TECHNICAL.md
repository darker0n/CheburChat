# Технический документ Чебурчата

Обзор архитектуры и протокола. Полный авторитетный источник — [MVP_SPEC.md](MVP_SPEC.md); здесь — сжато, для быстрого понимания.

## Архитектура

Chrome Extension, Manifest V3. Без сборки — грузится прямо из исходников.

```
content script (vk.js)  ──chrome.runtime.sendMessage──►  background service worker (worker.js)
   │  интеграция с DOM ВК, детекция, UI-маркеры                 │  вся крипта, хранилище, trust-логика
   └─ vk_pure.js (чистые хелперы, globalThis.__CHEBURCHAT_VK_PURE__)
popup — onboarding, бэкап ключа, список контактов, trust-действия
```

**Единый писатель.** Вся крипта, записи в `chrome.storage.local` и логика доверия — только в background-воркере. Content script никогда не пишет в хранилище напрямую: каждая операция идёт сообщением воркеру. Это осознанное решение про защиту от гонок при нескольких вкладках. Воркер делает per-record read-modify-write, без перезаписи всей базы.

MV3-воркер может усыпляться и перезапускаться, поэтому все крипто/хранилищные операции идемпотентны и не зависят от долгоживущего in-memory состояния.

## Криптопрофиль

- Библиотека: **OpenPGP.js**, ограниченный профиль.
- Ключи: **curve25519** (ECDH-шифрование) + Ed25519 (подпись). Без сжатия.
- Один долгоживущий ключ-идентичность на пользователя. Импорт/экспорт — armored-текст.
- **Подпись обязательна** для ключевых анонсов и для каждого сообщения (sign+encrypt одной операцией).
- **Шифрование «и себе» обязательно**: каждое сообщение шифруется публичным ключом получателя **и** отправителя — чтобы отправитель мог перечитать свою историю после перезагрузки.

## Протокол `CHEBURCHAT:v1`

Сообщения идут через обычный транспорт ВК как текст, но в детектируемой обёртке. Версия — всегда `v1`.

### Ключевой анонс — две строки
```
Я поделился с вами своим ключом шифрования CheburChat. Установите CheburChat, чтобы включить защищённый чат: https://cheburchat.com/install
CHEBURCHAT:v1:key:<base64url-utf8-json>
```
Первая строка — человекочитаемое приглашение (для тех, у кого нет расширения). Вторая — машинная нагрузка; именно она авторитетна. JSON (порядок ключей фиксирован для подписи): `v`, `platform`, `accountId`, `publicKeyArmored`, `fingerprint`, `displayName`, затем `sig` — base64url detached-подпись OpenPGP над каноническими байтами объекта без `sig`.

### Зашифрованное сообщение
```
CHEBURCHAT:v1:msg:<base64url>
```
Полезная нагрузка (до шифрования) — UTF-8 JSON c фиксированным порядком: `v`, `platform`, `accountId`, `ts` (RFC 3339 UTC, мс), `body`. Затем sign+encrypt к ключу контакта и собственному, бинарный OpenPGP-пакет → base64url.

`accountId` — всегда строка. `displayName` всегда присутствует (пустая строка, если неизвестно).

## Состояния доверия

Состояния контакта (приложение определяет их само, отдельно от терминологии OpenPGP): `missing` → `new` → `trusted`; `changed` при конфликте ключа; `rejected` при явном отклонении. Автошифрование — только для `trusted`. `decrypt_failed` — состояние уровня сообщения, на доверие контакта не влияет.

## Модель идентичности и хранилище

Идентичность платформенно-нейтральна: контакты и привязки ключуются парой `(platform, accountId)` (в MVP `platform = "vk"`). Это задел под будущие платформы (Max) без смены модели.

Ключи хранилища (`chrome.storage.local`), раздельные неймспейсы:
`identity`, `settings`, `binding:<platform>:<accountId>`, `contact:<platform>:<accountId>`.

## Валидация (главные гейты)

- **Приём анонса:** верный префикс/версия, парсинг JSON, валидная подпись, совпадение `platform`/`accountId` с реальным автором сообщения ВК и активным диалогом. Пересланные/вставленные чужие анонсы не меняют доверие.
- **Рендер расшифрованного:** успешная расшифровка, верная подпись, совпадение `platform`/`accountId` с автором сообщения (и с активным собеседником, либо с собственной привязкой — для своих сообщений).
- Смена в `changed` — только при новом анонсе с **другим** публичным ключом. `decrypt_failed` сам по себе никогда не означает `changed`.

## Лимиты

- Жёсткий лимит ВК — **4096** символов на финальный обёрнутый текст.
- Консервативный порог предупреждения — ~1800 UTF-8 байт plaintext (~1800 латиницы / ~900 кириллицы).
- При превышении — **блокировать** отправку (не обрезать), с понятной ошибкой.

## Модель угроз

- ✅ Защищает содержимое от **сервера ВК, сети/провайдера и СОРМ** — по проводу только шифротекст.
- ❌ Не защищает от: вредоносного ПО и скомпрометированного устройства/браузера; метаданных (кто/кому/когда — это видит ВК); скриншотов и буфера обмена.
- Расшифрованный текст рендерится inline в DOM ВК, ввод — в нативном поле ВК. Значит активный клиентский JS самого ВК технически имеет доступ к DOM/вводу — это **вне** модели защиты MVP (усиление — post-beta). Граница защиты — сервер/сеть, а не само устройство.

Приватный ключ в текущей бете хранится в `chrome.storage.local` без отдельного пароля — главный security debt, документирован, закрытие — post-beta.

- Кодирование транспорта — [base64url](https://datatracker.ietf.org/doc/html/rfc4648#section-5).
